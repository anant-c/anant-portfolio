How a Hash Table Works

Sample Channel 12:00 Watch on YouTube

Hash tables bridge an infinite key space to a finite memory array, providing constant-time lookups by carefully managing hash functions, collisions, and load factors.

TL;DR

  • Direct addressing is fast but unscalable: Using strings or UUIDs as memory indices would require billions of gigabytes of RAM.
  • Hash functions bridge the gap: They deterministically convert arbitrary keys into integers, scattering them uniformly to avoid predictable clustering.
  • Collisions are a mathematical certainty: The pigeonhole principle guarantees two keys will eventually share a bucket, handled via separate chaining (linked lists) or open addressing (probing).
  • Memory layout matters: Open addressing avoids pointer chasing and cache misses, making it the preferred strategy in high-performance modern languages.
  • Resizing guarantees performance: When the table reaches a ~0.75 load factor, it doubles in size and rehashes all elements, yielding an amortized O(1) insertion time.

The Direct Addressing Problem 00:00

If all application keys were small integers, like numbers between 0 and 99, we would never need complex data structures. We could allocate a contiguous array of 100 elements. Writing or reading a value for key 42 would mean accessing index 42 directly in O(1) time. The speaker notes that array indexing is the fastest operation hardware can perform, taking only a single multiplication and addition to compute the memory address.

The problem arises with real-world keys. A customer email address can be up to 250 characters long. The number of possible distinct strings is larger than the number of subatomic particles in the observable universe. Directly addressing every possible 64-bit integer would require billions of gigabytes of RAM. Since applications typically only need to store 1,000 to 10,000 items, mapping such a massive key space directly into memory is physically impossible.

The hash table bridge: from strings to physical memory offsets.

Hash Functions and Uniform Distribution 03:00

To bridge the massive key space and a moderately sized memory array (our bucket array, say of capacity 16), the speaker explains that we use a hash function. This mathematical bridge transforms an arbitrary sequence of bytes into a fixed-width 32-bit or 64-bit integer.

A hash table's function must meet three core requirements:

  • Deterministic: Passing the string "alice" a million times must yield the exact same numerical hash value. Without this, stored values would be permanently lost.
  • Computationally fast: The hash calculation must be quicker than scanning a linked list, otherwise the performance advantage vanishes.
  • Uniform distribution: Similar keys must be randomly scattered. Changing a single bit in the input (e.g., from "cat" to "car") should flip roughly 50% of the bits in the output hash. This property is known as the avalanche effect.

Once we have our large integer—say 3,800,000,000—we apply the modulo operator against the array's capacity (modulo 16). This yields a remainder between 0 and 15, which becomes the direct index for our array slot.

Collision Resolution Strategies 06:00

Because of the pigeonhole principle, mapping unpredictable keys into a finite array mathematically guarantees that two different keys will eventually hash to the same bucket index. If both "alice" and "bob" produce hashes that yield a remainder of 7, we have a collision. The data structure's overall design is defined by how it handles this inevitability.

Separate chaining uses pointers to heap-allocated nodes, while open addressing packs values contiguously.

1. Separate Chaining

In this model, each array slot holds a pointer to a singly linked list. When a collision happens at index 7, the new key-value pair is simply appended to the list at that index. Searching involves computing the hash, jumping to the bucket, and traversing the linked list.

This approach gracefully handles tables exceeding 100% capacity, but the CPU cache pays a hefty penalty. Modern architectures stall for hundreds of clock cycles on "pointer chasing" because linked list nodes are scattered unpredictably across the heap.

2. Open Addressing

Modern high-performance implementations typically prefer open addressing. Entries live directly in the bucket array with no secondary pointers. If index 7 is full, the algorithm probes the array sequentially (linear probing) to find an empty slot—checking 8, then 9, wrapping around to zero at the end of the array if needed.

While this provides extraordinary CPU cache locality since contiguous slots are fetched together, it suffers from a phenomenon known as primary clustering. Colliding keys form long contiguous blocks, forcing subsequent keys to traverse the entire cluster, making it grow even larger. Advanced hash tables use quadratic probing or double hashing to mitigate this.

Resizing and Load Factors 09:00

A hash table's performance degrades severely as it fills up. We quantify this fullness using the load factor (α): the number of stored elements (n) divided by the number of buckets (k). If you have 12 elements in 16 buckets, your load factor is 0.75.

As the load factor approaches 1, open addressing search times spike toward O(n) due to scanning dozens of filled slots, and separate chaining linked lists grow excessively long. To maintain speed, libraries set a maximum threshold (typically 0.70 or 0.75).

When crossed, the table automatically allocates a brand-new bucket array—usually double the size (e.g., jumping to 32 buckets). Crucially, the old elements cannot just be copied over. Because the divisor changed from 16 to 32, every key must be rehashed. A key that originally landed in slot 7 modulo 16 might now land in slot 23 modulo 32. This rehashing takes O(n) time, but amortized over all n insertions, the average cost per operation remains O(1).

Do This

  • Monitor your hash table's load factor and keep it below ~0.75 to preserve instantaneous lookup times.
  • Favor open addressing with linear probing over separate chaining when working in low-level systems where CPU cache locality heavily dictates performance.
  • Pre-allocate your table capacity if you know the final number of elements in advance, avoiding expensive O(n) resize operations.

Glossary

  • Avalanche Effect: A property where changing a single bit of a hash function's input flips roughly 50% of the output bits.
  • Separate Chaining: A collision resolution strategy where each array bucket points to a linked list of elements.
  • Open Addressing: A collision resolution strategy where elements are stored directly in the bucket array and probed sequentially.
  • Load Factor (α): The ratio of stored elements to the number of available buckets.
  • Amortized Analysis: Calculating the average cost per operation over a sequence, distributing the cost of occasional expensive operations (like resizing) across all standard operations.
