Why B-Trees Power Databases

Sample Channel Duration: 12:00 Watch on YouTube

B-trees solve the memory hierarchy mismatch by matching node capacity to the physical disk block, achieving high fanout and logarithmic height even for hundreds of millions of rows.

TL;DR

  • The latency gap between RAM and disk is 5 to 6 orders of magnitude; database performance is measured in total disk page transfers, not CPU instruction counts.
  • Binary trees fail on disk because their low branching factor (2) creates tall trees that demand too many sequential, random I/O operations and waste 99% of page bandwidth.
  • B-trees solve this by expanding the node size to exactly match the disk block size (e.g., 4KB), achieving fanouts of hundreds and flattening the tree to a height of 3 or 4 for hundreds of millions of records.
  • Modern databases use B+ trees, which segregate routing keys into internal nodes to increase fanout further, and link all data-holding leaf nodes in a continuous chain for optimal sequential range scans.

The Memory Hierarchy and Disk Block Transfers 00:00

While hash tables provide blazing fast O(1) lookups in main memory, the backbone of database storage engines like PostgreSQL, MySQL InnoDB, SQLite, and Oracle is the B-tree (and specifically the B+ tree). Database architects converged on this structure due to the stark reality of the hardware memory hierarchy.

CPU registers and L1 cache operate in less than a nanosecond, and RAM takes 50 to 100 nanoseconds. However, secondary storage (spinning disks or modern SSDs) operates in the microsecond to millisecond range. This presents a 5 to 6 order of magnitude latency gap.

"If fetching data from L1 cache is like grabbing a book from your desk, reading from disk is like boarding a transatlantic flight to borrow a book from a library in Europe." — 00:45

Because of this latency overhead, storage controllers do not transfer single bytes. The operating system always requests data in contiguous chunks called pages or blocks (typically 4KB, 8KB, or 16KB). Even to read four bytes, the system fetches an entire page.

"In database systems, the golden metric of algorithm performance is not CPU instruction count; it is the total number of disk page transfers." — 01:30

Why Binary Trees Fail in Secondary Storage 02:15

Standard balanced binary search trees (like AVL or Red-Black trees) are fundamentally mismatched for disk-based storage. With a branching factor of two, they grow tall and spindly. A binary tree holding one million elements has a height of roughly 20. Thus, a lookup requires traversing 20 sequential nodes.

Because nodes are created over time and scattered across random disk pages, finding one record requires 20 separate disk I/O operations. At 5 milliseconds per random read, a single query takes 100 milliseconds, destroying the possibility of handling thousands of concurrent transactions.

Furthermore, storing a small 16-byte binary node inside a 4KB disk page wastes over 99% of the transferred data. The hardware delivers 4,096 bytes, but the algorithm discards 3,980 of them.

Multi-Way Trees and B-Tree Balancing Invariants 04:30

Invented in 1970 by Rudolf Bayer and Edward McCreight, the core insight of the B-tree is to match the node size to the storage block size of the underlying hardware. Instead of one key and two children, a B-tree node is a "multi-way" node that occupies an entire 4KB or 8KB page, packing hundreds of keys and child pointers.

By increasing the branching factor (or fanout) from 2 to say, 500, the tree becomes dramatically wider and flatter. A tree with a branching factor of 500 can hold 125 million keys (500³) at a height of just 3. Searching 100 million records takes only three disk reads. In practice, the root and top levels are cached in RAM, meaning most queries require just one physical disk I/O.

A B-tree maintains strict balance through elegant mathematical invariants:

  • Let B be the maximum number of children. Every node except the root must contain at least ceil(B/2) children (the half-full rule).
  • All leaf nodes reside at the exact same depth from the root.
"A B-tree is self-balancing not by rotating nodes like an AVL tree, but by growing and shrinking from the top down." — 06:00

When an inserted key overflows a leaf node, the node splits in half. The median key pushes upward into the parent node as a separator. If the parent overflows, it splits too. The height of the tree only increases when the root splits, guaranteeing perfectly synchronized leaves.

B+ Tree Leaf Chains and Range Scans 07:30

Modern databases rely on a refined variant called the B+ tree. It makes two crucial modifications to the classic B-tree:

  1. Routing Keys Only: Internal nodes store strictly routing keys and child page pointers, not actual row records. All actual records (or pointers to them) are stored exclusively in the leaf nodes. This separation increases the fanout of internal nodes even further, allowing a 4KB page to hold over a thousand routing keys.
  2. Sequential Chaining: All leaf nodes are chained together with horizontal pointers, forming a doubly linked list of disk pages.
"This linked leaf chain is the secret weapon for relational databases." — 09:00

This linked list makes range queries incredibly efficient. To find all orders between January 1st and January 31st, a hash table would require a full table scan because hashing destroys sort order. A B+ tree, however, performs a fast O(log_B(N)) point lookup to find January 1st. Once at the leaf page, it follows the horizontal pointers, streaming contiguous pages sequentially until it reaches January 31st. It combines logarithmic point search speed with optimal sequential disk throughput.

Fig 2. B+ Tree architecture separating routing keys in internal nodes from actual records in the linked leaf chain.

Finally, to handle concurrent modifications and split operations safely, databases utilize write-ahead logging (WAL) and dirty-page buffer pools. Before modifying the tree pages in memory, structural changes are appended to a log, ensuring ACID durability and preventing catastrophic corruption in the event of a power failure mid-split.

Do this

  • When querying ranges of dates or numbers, ensure you have a B-tree index rather than a hash index on the column to take advantage of sequential leaf scanning.
  • Treat memory access and disk I/O as fundamentally different costs when designing or troubleshooting large-scale storage systems.

Glossary

  • Fanout: The branching factor, or maximum number of children a node can possess in a B-tree.
  • Page/Block: A contiguous chunk of bytes (e.g., 4KB, 8KB) requested by the operating system from disk as a single unit.
  • Write-ahead logging (WAL): Writing structural database changes to an append-only log before modifying tree pages in memory, guaranteeing durability.
